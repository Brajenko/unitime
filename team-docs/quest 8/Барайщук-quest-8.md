Код доступен в [репозитории Unitime](https://github.com/Brajenko/unitime/tree/quest-8-worker). [Постановка и статус](../../backend/app/api/connections.py) · [Воркер](../../backend/app/sync/tasks.py) · [Публикация в Redis](../../backend/app/sync/relay.py)

## 1. Сценарий

Пользователь запрашивает обновление подключённого календаря. Получение событий зависит от внешнего сервера и выполняется в отдельном процессе Celery. После обновления сохранённые интервалы используются в недельной сетке Unitime.

В качестве брокера согласовано использование Redis. Он уже передаёт задачи воркерам Celery, поэтому для синхронизации используется тот же брокер.

### Порядок обработки

1. `POST /api/connections/{id}/sync` проверяет владельца подключения. API сохраняет в PostgreSQL задание со статусом `queued`, идентификатором подключения и диапазоном дат, затем возвращает `job_id`.
2. Процесс публикации отправляет в Redis `job_id` и счётчик запланированных повторов. При первой отправке счётчик равен нулю. Тот же UUID используется как идентификатор задачи Celery. После отправки в PostgreSQL записывается `published_at`, а задание остаётся в `queued` до начала обработки.
3. Воркер получает сообщение и отмечает начало попытки в PostgreSQL. Затем он загружает события выбранных календарей и рассчитывает интервалы занятости.
4. Воркер фиксирует интервалы, `succeeded` и счётчик успешных записей `process_count` одной транзакцией. После коммита Celery отправляет подтверждение доставки (ACK).
5. Сетка несколько секунд проверяет состояние по `GET /api/connections/{id}/sync/{job_id}`, затем загружает сохранённую занятость. При успехе API статуса возвращает время обновления и число записанных интервалов.

### Статусы задания

| Статус | Когда устанавливается |
| --- | --- |
| `queued` | При постановке задания или после ошибки, для которой запланирован повтор. Статус сохраняется, пока задание ждёт публикации или свободного воркера. |
| `running` | Когда воркер начал обработку. При остановке до коммита в базе остаётся `running`. После повторной доставки тот же `job_id` получает следующий номер попытки. |
| `succeeded` | Когда PostgreSQL зафиксировал новые интервалы и результат задания. При повторной доставке статус сохраняется, а в журнале появляется `duplicate`. |
| `failed` | При окончательной ошибке, например при потере доступа к календарю, или после исчерпания повторов. Причина возвращается в поле `error`. |

При временной ошибке воркер сначала записывает время следующей попытки и переводит то же задание в `queued`, затем подтверждает текущую доставку. В журнале попытки различаются по номеру и имени воркера. Поле `attempts` считает начатые обработки, а `process_count` увеличивается при сохранении результата.

## 2. Запуск демонстрации

[Скрипт показа](quest8_demo.ps1) запускается из корня репозитория в PowerShell при работающем Docker Compose. Каждый прогон использует отдельный стенд и тестовый календарь с двумя известными интервалами. Подменяется скачивание `.ics`. Постановка, обработка и запись выполняются через API Unitime, Celery, Redis и PostgreSQL.

Вывод разделён на четыре этапа. Скрипт показывает постановку, публикацию, работу воркера и итог. Параметр `-Verbose` дополнительно выводит ответы API, строки журнала и снимки PostgreSQL для сравнения.

```powershell
$demo = '.\team-docs\quest 8\quest8_demo.ps1'
& $demo -Scenario normal -KeepOpen
& $demo -Scenario crash-before-commit
& $demo -Scenario crash-after-commit
```

В обычном прогоне до запуска воркера API вернул `queued`, а в Redis было одно ожидающее сообщение. Воркер A получил задание `91f2daec-7c28-4f92-8510-6874e8233e94` и записал результат. Статус изменился с `running` на `succeeded`, `process_count` стал равен 1. Для 22.11.2026 API сетки показал занятость с 10:00 до 11:00 и с 14:00 до 15:00 МСК. Запрос статуса от другого пользователя вернул `404`.

Параметр `-KeepOpen` оставляет обычный стенд запущенным. В терминале выводятся адрес Unitime, данные тестового входа и дата, которую нужно открыть в сетке. В браузере для обоих интервалов отобразились красные ячейки с подсказкой «Свободны: 0/1, заняты: 1». Стенд останавливается командой `& $demo -Scenario cleanup`.

| --- | --- | --- |
| Остановка до коммита | Прежняя занятость сохранится. Redis выдаст тот же `job_id`, второй воркер завершит задание. | До остановки был виден только прежний интервал и `process_count = 0`. Воркер B получил задание `ccb9e1c9-c298-409a-9073-3f4c1edf597c` с `redelivered=true`. Итог `succeeded`, две попытки, одна запись результата. |
| Остановка после коммита, до ACK | Второй воркер получит то же задание и увидит сохранённый результат. | Для `68fd8e63-e6f2-40b2-a30d-c86a96b13f60` воркер B записал `duplicate` с `redelivered=true`. ## 4. Согласованность и дополнительные проверки

Календарь уже подключён к моменту постановки. Строка `sync_jobs` хранит и состояние задания, и намерение опубликовать его в Redis. Если транзакция постановки откатилась, публиковать нечего. Если PostgreSQL сохранил строку, а Redis был недоступен, отдельный процесс публикации отправит её после восстановления Redis.

Отметка об отправке записывается после ответа Redis. При сбое между публикацией и этой отметкой сообщение может появиться повторно с тем же `job_id`. Если Redis потерял уже опубликованное сообщение, процесс публикации повторит отправку незавершённого задания после `visibility_timeout` и дополнительных 60 секунд без прогресса. В Redis включена запись AOF на постоянный том.

Воркер проверяет номер активной попытки под блокировкой строки задания. Интервалы и статус `succeeded` фиксируются одним коммитом. Подтверждение Celery отправляется после фиксации. Поэтому доставка завершённого задания пропускается, а попытка, уступившая место новой, теряет право на запись.

```powershell
& $demo -Scenario postgres-down
& $demo -Scenario redis-down
```

| Проверка | Наблюдение |
| --- | --- |
| PostgreSQL остановлен до коммита | Незакоммиченный результат остался невидимым. После ошибки записи доставка вернулась в очередь. Задание `f5f1fd24-afbe-48e4-a973-c57e1466bb38` завершилось со второй попытки, `process_count = 1`. |
| Redis остановлен до публикации | В PostgreSQL сохранилось задание `cdd6d228-5288-49ac-a5df-6aa542b19806` без отметки публикации. После запуска Redis опубликован и завершён тот же `job_id`. |
| Потеря сообщения и запоздалая попытка | Сообщение задания планировщика удалили из тестовой очереди и выставили время последней активности за пределы порога восстановления. Процесс публикации вернул сообщение с тем же ID. При двух начатых попытках результат сохранила только последняя. |
| Миграция | На тестовой базе с данными Quest 7 применили ревизию `0003_quest8_sync_jobs`, выполнили откат и применили её снова. Учётная запись и команда сохранились, `alembic check` не выявил расхождений. |

Все 38 тестов бэкенда прошли, включая шесть интеграционных. Пять сценариев демонстрации завершились с `PASS`.
