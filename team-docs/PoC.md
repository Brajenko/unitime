## 1. Самое рискованное допущение

> Пары и занятость студента реально оказываются в календаре, который можно привязать, и студент доходит до конца привязки.

Почему именно это: 7 из 18 держат расписание в HSE App X, а архитектура рассчитывает, что студент сам выгрузит пары в личный календарь. Если это не работает, продукт деградирует до When2Meet. Проверяется в W7.

## 5. Архитектура: монолит или микросервисы

**Выбор:** модульный монолит. API и воркер Celery собираются из одной кодовой базы, у них одна база Postgres.

Обоснование (дописать по результатам W2 и W10):
- маленькая команда и одна доменная модель (команда, участник, занятость, слот);
- отдельно масштабировать нужно только воркер, и для этого хватает отдельного процесса;
- провайдеры изолированы через порт `CalendarSourcePort`, а не через отдельные сервисы.

**Критический путь:** капитан создаёт команду → участник привязывает календарь → синк → сетка → фиксация. Слабые звенья — привязка и синк (B1, B2, T3, T5).

## 6. CAP по операциям

| Операция | Выбор | Что видит пользователь |
| --- | --- | --- |
| Фиксация слота, состав команды | CP | при недоступной базе: «не удалось зафиксировать, попробуйте позже»; двойной фиксации нет |
| Чтение сетки | AP | сетка по последним данным с пометкой «обновлено N мин назад» |
| Синк календарей | AP, eventual consistency | изменения появляются с задержкой до интервала опроса |

## 7. План деградации

Пороги уточнить по результатам W2.

| Триггер | Что выключаем / упрощаем | Кто отвечает | Как возвращаем |
| --- | --- | --- | --- |
| p95 сетки > 500 мс | кворум-поиск и ранжирование; отдаём «все свободны» из кеша | | p95 < 200 мс 10 минут подряд |
| ошибки CalDAV > 20% | автосинк; остаётся кнопка «обновить» | | ошибки < 5% |
| Redis недоступен | Celery на паузе, чтение напрямую из Postgres | | Redis поднят, очередь разобрана |
