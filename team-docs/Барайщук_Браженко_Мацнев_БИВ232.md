## Сценарий

Участник подключает календарь по ссылке и открывает сетку. Он ожидает увидеть время, куда помещается встреча нужной длины, и занятое по расписанию время в этих окнах не должно появляться.

Отдельной кнопки поиска и списка окон в коде нет. Поиск запускается при открытии сетки, а окна подсвечиваются в её клетках. Проверка выполнена для одного пользователя, режим команды идёт через тот же код и покрыт интеграционными тестами.

## Что работает сегодня и что ещё не работает

Путь по публичной ссылке выполнен целиком до ответа API на реальном расписании. Заглушек и моковых данных на этом пути нет

Адаптеры Google, Яндекса и Apple есть в `backend/app/adapters`. Google подключён через REST `freeBusy`, а CalDAV используют Яндекс и Apple.

Сценарий заканчивается показом слотов. Фиксации слота, ручного ввода окон и Telegram-бота в коде нет.

## Как запустить и повторить проверку

Использовались Docker 29.9.2 и Compose v5.6.1, в контейнерах Python 3.12.16 и PostgreSQL 16.15. Для пути по ссылке в `.env` достаточно своего значения `APP_SECRET`, переменные `GOOGLE_*` и `YANDEX_*` можно оставить пустыми.

Запуск проекта.

```bash
cp .env.example .env
docker compose up --build
```

Ручная проверка в браузере на `http://localhost:3000`.

1. Зарегистрируйтесь по email и паролю.
2. Нажмите «Подключить календарь», выберите плитку «Ссылка на календарь», вставьте свою публичную ссылку на `.ics` и подтвердите выбор календаря.
3. На сетке нажмите «Обновить» и откройте неделю, где есть занятия. Диапазон не длиннее 14 дней.
4. Занятые клетки должны совпасть с событиями из вашего календаря, а при наведении на зелёную клетку должен появиться слот.


Проверки из README. Тесты запускаются на отдельной базе, потому что интеграционные тесты очищают таблицы.

```bash
cd backend
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
pytest
```

## Решение 1. Обновлять календари в фоновом воркере

**Какую задачу решает.** Пользователь не должен зависеть от скорости внешнего календаря. Обновление вынесено в отдельный процесс, а сетка строится из базы. Если провайдер недоступен, данные прошлого обновления остаются в базе.

**Где видно.** `backend/app/sync/tasks.py`, `backend/app/celery_app.py`, сервисы `worker` и `beat` в `docker-compose.yml`.

**Какой вариант рассматривали.** В `team-docs/poc-presentation.md` отвергнут опрос календаря внутри запроса пользователя (риск R4) и отдельный сервис синхронизации со своей базой (ADR-1). Воркер подходит, потому что команде из трёх человек хватает одного кода с разными режимами запуска, а новый сервис выигрыша при нынешней нагрузке не даёт.

**Что работает сегодня и что запланировано.** Сегодня в коде `beat` ставит синхронизацию всех активных подключений раз в 15 минут, а `WeekGrid.tsx` при открытии сетки ставит обновление своих подключений и ждёт его конца. Это вариант A из `Практика-5`, его решено заменить. Планируется, чтобы сетка открывалась сразу по сохранённым данным с датой и временем последнего обновления, а синхронизация шла только в фоне. Участников будут синхронизировать в разное время, активных раз в 15 минут, неактивных реже. Это варианты B и D из `Практика-5`, они ещё не реализованы. Реализация появится в `WeekGrid.tsx` (функция `loadRange` перестанет ждать обновления), в `backend/app/sync/tasks.py` (разные интервалы для активных и неактивных) и в `backend/app/celery_app.py` (расписание `beat`). Время последнего обновления в API уже есть, это поле `last_synced_at` в ответе `GET /api/grid`.

## Решение 2. Хранить только интервалы занятости

**Какую задачу решает.** Для поиска окна нужны только начало и конец события, а названия личных событий сервису не нужны. По данным `team-docs/poc-presentation.md`, 8 из 18 опрошенных дали бы календарь только без личных событий.

**Где видно.** Модель `BusyIntervalRow` в `backend/app/models.py` не имеет поля для названия, `backend/app/adapters/ical.py` его не читает, а `backend/app/security.py` шифрует секреты подключений через AES-GCM.

**Какой вариант рассматривали.** В ADR-3 отвергнуто хранение событий целиком со скрытием названий в интерфейсе, потому что утечка базы раскрыла бы названия. Текущий вариант подходит, потому что он проще и проверяется выгрузкой базы. Минус в том, что показать название занятия в сервисе нельзя.

## С какого файла команда продолжит работу

Следующий шаг по плану в `team-docs/poc-presentation.md` это фиксация слота. Начинать стоит с новой модели в `backend/app/models.py`, затем добавить обработчик в `backend/app/api` и выбор клетки в `frontend/src/pages/WeekGrid.tsx`.

Ложные окна до первого обновления предлагаем исправить отдельно в `backend/app/services/grid.py`. Это предложение автора разбора, команде нужно его подтвердить.
